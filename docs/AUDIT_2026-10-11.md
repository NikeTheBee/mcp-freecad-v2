# Audit complet — MCP FREECAD

> Date : 2026-10-11 · Commit audité : `5b388b3` (master, dernier commit le 2026-07-06)
> Environnement : Windows 11, FreeCAD 1.1.1 (`A:\FreeCAD`), bridge sous Python 3.13.12,
> base `blwfish/freecad-mcp` clonée en `7df5412` (branche `dev`, 2026-06-22).
> Preuves reproductibles : scripts et sorties dans [`docs/audit_2026-10-11/`](audit_2026-10-11/).

## 0. En clair (à lire en premier)

- **La suite de tests officielle passe : 30/30 en 35 s.** Mais elle vérifie surtout que « quelque chose
  est produit », pas que c'est **juste**. Sous attaque, presque toutes les couches maison cassent.
- **6 défauts graves confirmés par exécution réelle** :
  1. **La CAM génère du G-code dangereux** : elle perce 4 « trous » dans une pièce qui n'en a aucun
     (elle prend les congés pour des trous), avec une **avance F0** et **sans jamais démarrer la broche**.
  2. **Le rollback (`checkpoint.restore`) ne revient pas en arrière** : il renvoie le document déjà
     modifié en mémoire, et deux noms de checkpoint différents peuvent écraser le même fichier.
  3. **`verify` dit « OK » à tort** : sur un fil sans solide, sur une pièce dont le recalcul a échoué,
     et sur deux solides qui s'interpénètrent. Le contrôle d'auto-intersection est du **code mort**.
  4. **La nomenclature (BOM) est fausse** : 5 lignes au lieu de 2 pièces, une boîte et un cylindre
     fusionnés en « Bracket ×2 », les instances `App::Link` comptées à part.
  5. **Une installation neuve aujourd'hui est cassée** : 7 des 9 patches ne s'appliquent plus sur la
     base upstream actuelle → plus d'authentification maison, autostart cassé, bridge à moitié patché.
  6. **Le jeton d'authentification fuit** vers n'importe quel processus local qui occupe le port 23456
     avant FreeCAD, et ce processus peut injecter du texte arbitraire dans les réponses lues par l'IA.
- **Points forts réels** : rapidité (2,7 ms par appel), serveur socket robuste (fuzzing, 200 requêtes
  concurrentes sans erreur), historique git propre, aucun secret, solveur cinématique sérieux,
  bonne intuition d'architecture (mémoire / vérification / checkpoints / skills à la demande).
- **Verdict : prototype avancé, pas prêt pour un usage par un tiers. La CAM ne doit jamais toucher
  une machine en l'état.**
- **Plan détaillé fonctionnalité par fonctionnalité (retirer / corriger / améliorer / créer) : §7.**
- **Avis final pour l'objectif confirmé (usage personnel, open source, non vendu) : §8 — garder et
  réparer, environ 2 semaines.** La piste « grand industriel » ([`PRODUCTION_GRANDE_ECHELLE.md`](PRODUCTION_GRANDE_ECHELLE.md))
  est hors périmètre.
- **Conclusion (§6) : on GARDE le projet, mais on REFOND la plomberie.** Pas de repartir de zéro :
  le code maison ne représente que ~7 % du code exécuté, les défauts sont localisés et corrigeables,
  et une réécriture complète referait exactement les mêmes choix (même base upstream).

## 1. Périmètre et méthode

### 1.1 Ce que contient réellement le projet

| Bloc | Lignes | Remarque |
|---|---:|---|
| Code maison exécuté (`server/freecad_layers` + `server/bridge_patches`) | **1 426** | 11 modules + 2 patches |
| Outillage d'install (bootstrap, patcheur, runner, scan) | 754 | |
| Tests + exemple | 1 832 | 28 scripts de test |
| Documentation + skills (Markdown) | 1 734 | 15 skills, CDC, roadmap, gap analysis… |
| **Base upstream `blwfish/freecad-mcp` (non versionnée ici)** | **19 677** | 36 outils MCP, socket, handler |

Le cœur fonctionnel (le serveur MCP et ses 36 outils) est **upstream**. Le projet est une
**surcouche** : patches injectés par remplacement de chaînes, couches Python appelées via
`execute_python`, skills (connaissance métier) et installeur.

### 1.2 Ce qui a été testé

1. Suite officielle `install/run_all_tests.py` (complète, avec greffes, socket et boucle MCP).
2. **Tests adverses des couches maison** sous `freecadcmd` (`adv_layers.py`, `adv_layers2.py`).
3. **Fuzzing, charge et concurrence** sur le socket `localhost:23456` (`adv_socket.py`).
4. **Usurpation de port** par un faux serveur local (`fake_server.py`).
5. **Crash volontaire** de FreeCAD et récupération par l'autostart.
6. **Limites de taille** des réponses (50 Ko) et des jobs asynchrones, via les vrais outils MCP.
7. **Scénario langage naturel de bout en bout** via les outils nommés (plaque percée).
8. **Coût en tokens** des schémas d'outils (`tools_cost.py`).
9. **Compatibilité avec l'upstream actuel** : application des patches sur `origin/main` et `origin/dev`.
10. Revue statique ligne à ligne de tout le code maison, des tests, de l'installeur et de la doc.

### 1.3 Ce qui n'a PAS été testé (limites de l'audit)

- Installation neuve réelle sur machine vierge (elle aurait écrasé la config actuelle) : remplacée par
  l'application des patches sur des copies de l'upstream actuel, ce qui suffit à prouver la casse.
- Mode GUI de FreeCAD, Linux et macOS.
- G-code sur une vraie machine (heureusement).
- Les greffes (Rocket, AirPlaneDesign, CROSS) au-delà de ce que couvre la suite.

## 3. Critique sans complaisance

> Consigne reçue : être « le méchant ». Chaque reproche ci-dessous est étayé par un test ou une ligne
> de code. Les points positifs sont listés en §3.10, parce qu'une conclusion honnête en a besoin.

### 3.1 « Secure by design » : surtout du marketing

- Le projet expose `execute_python`, c'est-à-dire **l'exécution de code arbitraire**. À côté, les
  « gates » `safe_out_path`/`safe_under` ont le poids d'une serrure sur une porte de grange : l'IA (ou un
  document piégé) peut écrire où elle veut avec une ligne de Python.
- `safe_out_path` ne confine **rien** : n'importe quel chemin absolu est accepté
  ([__init__.py:39-48](../server/freecad_layers/__init__.py#L39)). Le contrôle d'extension se contourne
  avec un flux NTFS alterné (`evil.exe:x.csv`). Le « pas d'écrasement » a une fenêtre TOCTOU.
- Les outils upstream (`mesh_operations export_*`) écrasent des fichiers sans rien demander : la
  politique « en un seul endroit » ne couvre que 1 426 lignes sur ~21 000.
- **Authentification à sens unique** : le client prouve qu'il connaît le jeton, le serveur ne prouve
  rien. Un processus local (autre session, malware sans droits admin) qui écoute le port 23456 en
  premier **reçoit le jeton et tout le code envoyé**, et peut renvoyer du texte que l'IA lira comme un
  résultat FreeCAD. Prouvé (§2.3).
- **Échec silencieux en mode ouvert** : si `mcp_auth.py` manque ou ne se charge pas, le handler patché
  met `_mcp_auth = None` et **désactive l'authentification sans le dire**
  ([apply_bridge_patches.py:151-168](../install/apply_bridge_patches.py#L151)).
- Le scanner de secrets **rate** les clés Anthropic (`sk-ant-…`), OpenAI projet (`sk-proj-…`),
  HuggingFace, Google, et toute affectation non quotée (`ANTHROPIC_API_KEY=…`). Pour un projet piloté
  par Claude, c'est précisément la clé la plus probable ([security_scan.py:21](../install/security_scan.py#L21)).
- L'installeur clone la base **sans épinglage** ([bootstrap.py:28](../install/bootstrap.py#L28)) :
  ~20 000 lignes de code exécuté dans FreeCAD, tirées de la tête de branche d'un seul mainteneur, sans
  vérification de hash. Deux greffes (AirPlaneDesign, CROSS) ne sont pas épinglées non plus.
- Journaux d'opérations : tout le code et tous les résultats (donc la propriété intellectuelle des
  pièces) en clair, sans rotation ni rétention.

### 3.2 Des tests verts qui ne prouvent pas que c'est juste

30/30, mais le rollback ne revient pas en arrière, la BOM compte faux, la vérification dit OK à
tort, et la CAM perce des trous fantômes à avance nulle. Les tests ont été écrits **après** le code,
**pour** le code : ils vérifient « ça produit un fichier non vide », pas « le contenu est correct ».
Aucun test ne vérifie une coordonnée de perçage, une quantité de BOM sur un vrai assemblage, ou qu'un
rollback restaure le contenu du disque. Un test ignoré compte comme réussi. La CI, elle, ignore
justement les parties qui cassent (intégration Windows, socket, auth, autostart).

### 3.3 La CAM est dangereuse — l'étiquette « ✅ basic » est irresponsable

`_hole_faces` prend **toute** face cylindrique pour un trou : congés, bossages, surface extérieure d'une
barre ([cam.py:31-37](../server/freecad_layers/cam.py#L31)). L'outil par défaut est une fraise Ø5 quel
que soit le diamètre du trou, sans vitesse ni avance (`F0.00`), et le post ne démarre jamais la broche.
Le cas d'erreur du post écrit le `repr()` Python dans le fichier `.nc` ([cam.py:67](../server/freecad_layers/cam.py#L67)).
Sur une vraie CNC : fraise plongée à l'arrêt dans la matière, casse outil au mieux. Pour un public
« zéro code » qui ne sait pas lire du G-code, c'est le pire endroit pour être optimiste.

### 3.4 La vérification géométrique ment

- `ok` ne demande pas qu'il y ait un solide ([verify.py:60](../server/freecad_layers/verify.py#L60)).
- L'état de l'objet (`Invalid`, `Touched`, erreur de recalcul) est ignoré : on valide la **dernière
  forme valide**, pas la pièce actuelle.
- `Shape.check(True)` **lève une exception** quand il trouve un problème. Le code l'avale avec
  `except Exception: pass` ([verify.py:53-58](../server/freecad_layers/verify.py#L53)). Le contrôle
  d'auto-intersection, promis par la skill et le CDC, **n'a jamais rien signalé**.
- Pire : [skill-assembly](../skills/skill-assembly/SKILL.md) dit à l'IA de détecter les interférences
  d'un assemblage avec `Part.makeCompound` + `skill-verify`. Sur deux pièces qui s'interpénètrent :
  « OK ». L'IA est **activement guidée** vers un faux positif.
- Les contrôles annoncés au CDC (contraintes d'esquisse satisfaites, masse plausible) n'existent pas.

### 3.5 Le rollback ne fait pas de rollback

- Le nom est « assaini » par une regex lossy ([checkpoint.py:24-26](../server/freecad_layers/checkpoint.py#L24)) :
  `"v1/fins"` et `"v1 fins"` partagent le même fichier, écrasé silencieusement par `saveCopy`
  (qui, lui, ne passe pas par `safe_out_path` — la règle « secure by design » n'est même pas
  appliquée au module qu'elle protège).
- `restore` appelle `FreeCAD.openDocument` : si le document est déjà ouvert (cas normal après un
  premier restore), FreeCAD rend **l'instance en mémoire, modifications comprises**. « Revenir au
  checkpoint avant les ailerons » rend… la version avec les ailerons ratés.
- Le document fautif reste ouvert à côté, l'actif change sans prévenir.

### 3.6 La mémoire projet est fragile et mal placée

- Un `state.json` corrompu fait planter `summary()`, c'est-à-dire **le premier appel de chaque session**.
- Aucun verrou : deux sessions (Claude Code + Claude Desktop, deux onglets) font du
  lire-modifier-écrire concurrent → pertes de mises à jour.
- `STATE_VERSION` existe mais aucune migration ; un champ manquant = `KeyError`.
- **Un seul projet par clone du dépôt**, stocké **dans le dépôt de code**. Pour travailler sur deux
  conceptions, il faut deux clones ou jongler avec une variable d'environnement.
- Le résumé n'a aucune limite de taille : la promesse « token-minimal » s'effondre sur un vrai projet.
- Doublon : l'upstream propose déjà `view_control checkpoint / rollback_to_checkpoint`. Deux systèmes
  de checkpoints concurrents, l'IA ne sait pas lequel utiliser.

### 3.7 L'installation « une commande, idempotente, multi-OS » ne tient pas

- Cassée sur l'upstream actuel (§2.6), et ne s'arrête pas quand les patches échouent.
- [bootstrap.py:193-198](../install/bootstrap.py#L193) : si `claude_desktop_config.json` est
  illisible, il repart d'un dict vide et **écrase toute la config Claude Desktop** de l'utilisateur
  (tous ses autres serveurs MCP), sans sauvegarde ni écriture atomique.
- `clone_or_update` ne met **jamais** à jour (« exists, skipping »). Le nom ment ; il n'y a aucun
  chemin de mise à jour.
- `pip install --upgrade` dans le **Python système** de l'utilisateur, pas dans un venv.
- Sur la machine de référence elle-même, l'état ne correspond pas à ce que produit le bootstrap :
  AICopilot est dans `%APPDATA%\FreeCAD\Mod` (non versionné), absent de `v1-1\Mod` et de
  `~/.freecad-mcp/AICopilot`. Le lanceur de secours [start-freecad-server.bat:12](../start-freecad-server.bat#L12)
  pointe vers le dossier non versionné : après un vrai bootstrap, **le plan B ne marche pas**.
- Chemins `A:\FreeCAD\...` codés en dur dans le bootstrap, l'autostart, le runner et le `.bat`.
- « Multi-OS » : jamais exécuté hors Windows, à part le sous-ensemble CI sur Linux.

### 3.8 Une architecture de « patcheur » sur un upstream qui court plus vite

Le projet modifie le code d'un tiers par **remplacement exact de chaînes**. L'upstream a fait 300+
commits en 3,5 mois ; 7 ancres sur 9 sont déjà mortes. C'est un tapis roulant de maintenance : chaque
mise à jour upstream casse le projet, et chaque correctif upstream (sécurité comprise) est retardé
tant qu'on ne refait pas les patches. Le projet est inactif depuis le 2026-07-06 : il est déjà décroché.

Et la valeur maison n'est accessible **que** par `execute_python` avec du `sys.path.insert` à la main,
alors que le `CLAUDE.md` impose « préférer les outils nommés ». Le chemin d'accès à la valeur du
projet est le plus dangereux et le plus coûteux en tokens.

### 3.9 Largeur au lieu de profondeur, et documentation qui se contredit

- 15 domaines (fusée, drone, robotique, FEM, CAM, engrenages, TechDraw, cinématique, BOM, fixations…),
  chacun en 50–200 lignes avec **un** test nominal. Rien n'est au niveau production. Le propre
  anti-pattern du `CLAUDE.md` (« une capacité à la fois, validée ») est respecté à la lettre, pas
  dans l'esprit : la validation est trop faible pour mériter le ✅.
- Le README dit à la fois « CAM needs FreeCAD 1.2-dev » ([README.md:49](../README.md#L49),
  [README.md:81](../README.md#L81)) et « CAM ✅ basic sur 1.1 » ([README.md:78](../README.md#L78)).
  La ROADMAP dit que `skill-cfd`/`skill-cam` sont absents alors qu'ils existent. « ~32 outils » pour 36.
- Les rapports de réussite (`RAPPORT_TEST_MCP.md` « RÉUSSI », GAP_ANALYSIS « ✅ Fait ») sont rédigés
  par la même IA qui a écrit le code, sans revue indépendante. Le test « pince » est une belle
  **analyse** d'un STEP existant ; ce n'est pas une **conception** en langage naturel, et les plans 2D
  exigés par le sujet n'avaient pas été produits.
- Licence CC BY-NC 4.0 pour du logiciel : Creative Commons déconseille elle-même ses licences pour du
  code ; non reconnue OSI ; la clause NC empêche de reverser les correctifs à l'upstream (LGPL-2.1)
  et freine toute adoption.

### 3.10 Ce qui est réellement bon (pour être juste)

- **Performance et robustesse du transport** (upstream) : latence de quelques ms, fuzzing encaissé,
  concurrence parfaite, flood non authentifié rejeté proprement.
- **Le diagnostic produit est bon** : mémoire projet, vérification texte, checkpoints, skills à la
  demande, CLAUDE.md court. Les idées sont les bonnes ; c'est l'exécution qui est fragile.
- `kinematics.py` (solveur de dyades, bielle-manivelle, quatre-barres) : propre, sans dépendance,
  validé à 3 µm sur une vraie pièce.
- `urdf_aug.py` : validation des noms ROS, génération propre. `aero.py` : formules correctes.
- Écriture atomique du `state.json`, neutralisation de l'injection CSV, anti-traversal sur les
  checkpoints : de bons réflexes.
- Historique git propre (aucun secret, aucun chemin personnel, identité no-reply), CI existante,
  suite rapide (35 s), documentation abondante et honnête sur certaines limites (R1–R11).

### 4.3 P1 — Refondation technique · ~1 à 1,5 semaine

1. **Se rebaser sur l'upstream `main` actuel**, épinglé par SHA, et **supprimer le patch d'auth maison** :
   l'upstream a désormais sa propre authentification (CWE-306).
2. **Supprimer le patching par chaînes.** L'autostart Windows devient soit une contribution (PR) à
   `blwfish/freecad-mcp`, soit un petit **lanceur enveloppe** (script qui démarre FreeCAD puis le bridge),
   sans modifier le code tiers.
3. **Supprimer l'usurpation de port** par une **authentification mutuelle** : le serveur doit prouver
   qu'il connaît le jeton **avant** que le bridge n'envoie quoi que ce soit (défi-réponse HMAC dans les
   deux sens). Option simple sous Windows : un named pipe via `multiprocessing.connection`
   (`Listener`/`Client` avec `authkey`, qui fait déjà le défi-réponse dans les deux sens), en
   n'utilisant que `send_bytes`/`recv_bytes` (jamais `send`/`recv`, qui passent par pickle).
   NB : `AF_UNIX` n'est **pas** disponible dans CPython sous Windows (vérifié sur Python 3.13 et sur
   le Python 3.11 de FreeCAD) ; ce n'est donc pas une option.
4. **Exposer les couches comme de vrais outils MCP** (un second serveur `freecad-layers`, ou un
   plugin upstream) : `verify_object`, `checkpoint_save/restore`, `project_summary`, `bom_export`, … Plus
   de `sys.path.insert` dans `execute_python`, moins de tokens, permissions par outil.
5. **Mémoire projet v2** : verrou de fichier, migration de schéma avec valeurs par défaut, `.bak` +
   récupération en cas de corruption, un dossier par projet hors du dépôt de code
   (`~/.mcp-freecad/projects/<nom>/`), résumé borné (N dernières features + compteurs).
6. **BOM v2** : parcourir l'arbre structurel (Body = 1 pièce via sa pointe, ignorer les features internes
   et les objets consommés par un booléen via `InList`, résoudre `App::Link`), grouper par signature
   géométrique (volume, aire, dimensions de boîte triées, inertie) et non par nom.
7. **Résilience** : après la mort détectée du processus, relancer immédiatement (backoff exponentiel au
   lieu d'un gel fixe de 120 s) avec un message exact ; **autosauvegarde périodique** des documents
   ouverts dans un dossier de récupération (principe CDC §1.3-3) ; restauration proposée au redémarrage.
8. **Limite de 50 Ko** : renvoyer une erreur explicite et immédiate (« résultat trop gros : N Ko »), ou
   découper / tronquer avec indication ; aligner les maximums documentés (`list_objects` ≤ 500) sur ce
   qui passe réellement ; corriger le retour d'`execute_python_async`.
9. **Venv dédié** (ex. `uv`) pour le bridge au lieu du Python système.

### 4.4 P2 — Qualité et produit · ~1 semaine

1. **Intégrer les tests adverses** de ce rapport à la suite (ils sont prêts dans
   `docs/audit_2026-10-11/`), et ajouter des tests d'**exactitude** : coordonnées de perçage, quantités
   de BOM sur un vrai assemblage, contenu disque après rollback.
2. **Un skip n'est jamais un pass** : statut `SKIP` distinct dans le runner.
3. **CI Windows** (`windows-latest` + FreeCAD portable) pour couvrir la plateforme cible, socket et auth
   compris ; instance FreeCAD de test sur un **port dédié**, jamais `taskkill /IM`.
4. Remplacer `security_scan.py` par **gitleaks** ou trufflehog en CI.
5. **Hygiène des journaux** : rotation, rétention (ex. 14 jours), journalisation du code en opt-in.
6. **Budget tokens comme métrique de régression** : taille des schémas, tokens par scénario type ;
   **profils d'outils** (« core » 8–10 outils vs « full » 36) ; sorties compactes par défaut.
7. **Documentation à source unique** : un tableau de capacités généré depuis les résultats de tests.
8. **Licence** : passer à une licence logicielle (MPL-2.0, Apache-2.0 ou LGPL-2.1 comme l'upstream) ;

## 6. Conclusion : garder et upgrader, ou repartir de zéro ?

### 6.1 Ce que « repartir de zéro » voudrait dire concrètement

Personne ne réécrirait sérieusement un serveur MCP FreeCAD de ~20 000 lignes et 36 outils : un « vrai »
redémarrage repartirait **de la même base upstream**. On referait donc la même surcouche (mémoire,
vérification, checkpoints, skills), en jetant au passage 1 800 lignes de tests, 1 700 lignes de
connaissance métier (skills, CDC) et le retour d'expérience accumulé. Le gain serait faible, le coût
réel.

### 6.2 Où sont vraiment les défauts

| Catégorie | Modules | Part des 1 426 lignes maison | Décision |
|---|---|---:|---|
| Sain, à garder tel quel | `kinematics`, `aero` (+ validation d'entrées), `urdf_aug`, `robotics` — plus skills, CDC, harnais de tests | ~36 % | **Garder** |
| Bonne idée, implémentation à corriger | `verify`, `checkpoint`, `state`, `drawing`, `bom`, gates de `__init__` | ~43 % | **Corriger** |
| Mauvaise approche | patches par chaînes (`mcp_auth`, `freecad_autostart`), `cam` — plus la logique de patch du bootstrap | ~20 % | **Jeter et refaire** |

Les défauts graves sont **localisés** (quelques fonctions), pas diffus. Le seul vrai défaut
d'architecture — modifier le code upstream au lieu de s'y brancher — se corrige en **supprimant**
du code, pas en en écrivant.

### 6.3 Verdict

> **GARDER le projet, REFONDER la plomberie. Ne pas repartir de zéro.**
>
> Concrètement : une branche `v2` dans ce même dépôt qui (1) applique P0 immédiatement,
> (2) se rebase sur l'upstream `main` épinglé, supprime tous les patches par chaînes et l'auth
> maison, (3) expose les couches maison comme de vrais outils MCP, (4) n'ajoute **aucun** nouveau
> domaine avant que les critères du §4.5 soient remplis.
>
> Effort estimé : **~3 semaines** de travail concentré (P0 + P1 + P2), contre au moins autant pour
> un redémarrage qui perdrait en plus les tests, les skills et le recul acquis.

**Le repositionnement qui donne du sens au projet :** arrêter d'être « un fork par patches » de
`blwfish/freecad-mcp`, et devenir **le pack « fiabilité + savoir-faire »** qui se branche dessus :
vérification géométrique qui ne ment pas, mémoire projet robuste, checkpoints fiables, skills métier.
C'est exactement ce que l'upstream n'a pas, et c'est là que ce projet a une vraie valeur. Les
correctifs génériques (autostart Windows, limites de trame) gagnent à être proposés à l'upstream.

**Seul cas où repartir de zéro se justifierait :** si l'objectif « IA locale » devient prioritaire à
court terme. Il faudrait alors un serveur minimal à 8–10 outils compacts conçu pour des petits
contextes, et l'upstream à 36 outils deviendrait un frein. Ce n'est pas l'objectif actuel affiché
(Claude est le client de référence) : ce scénario reste une option pour plus tard, pas une raison de
tout jeter maintenant.

> **sans finalité commerciale**. La cible « grand industriel »

> uniquement comme référence.

### 8.1 Verdict

> **GARDER le projet et le RÉPARER. Ne pas repartir de zéro.**

Pour un seul utilisateur sur sa propre machine, les cinq blocages industriels tombent :
`execute_python` est acceptable (c'est ta machine et ton code), l'IA cloud est acceptable (ce sont
tes données), la dépendance à l'upstream est acceptable (à condition de s'y brancher proprement au
lieu de le patcher), et la montée en charge est sans objet. Les défauts qui restent sont **localisés
et corrigeables** en environ deux semaines.

### 8.2 Ce que « sans bug » doit vouloir dire ici

Trois règles, dans cet ordre. Tout le reste est secondaire.

1. **Ne jamais mentir** : aucun « OK » sur une pièce fausse (verify, BOM, plans).
2. **Ne jamais perdre le travail** : rollback qui marche, sauvegarde automatique, reprise après crash.
3. **Ne jamais produire un fichier dangereux** : pas de G-code non validé.

### 8.4 Ce qui devient facultatif pour un usage personnel

N3 (authentification mutuelle), A7 (CI Windows), N5 (multi-projets), A5 (journaux), A6 (épinglage
des greffes peu utilisées), N7 (validateur G-code — seulement si tu veux un jour réactiver la CAM).

### 8.5 La licence

« Open source » au sens strict (définition OSI) exclut les clauses « non commercial ». Deux choix
cohérents avec ton objectif :

- **Tu veux surtout que personne ne vende ton travail** → garder une clause non commerciale, mais
  avec une licence faite pour le logiciel : **PolyForm Noncommercial 1.0** plutôt que CC BY-NC. Le
  projet sera alors « source disponible », pas « open source » au sens OSI.
- **Tu veux surtout des contributeurs et pouvoir reverser tes correctifs à l'upstream** → **LGPL-2.1**,
  comme `blwfish/freecad-mcp` et les ateliers greffés. Quelqu'un pourrait alors l'utiliser
  commercialement, mais toute modification du code devrait rester ouverte.

## 11. Campagne d'exactitude (2026-10-14)

Méthode : chaque opération comparée à une valeur connue d'avance (volume exact, formule de
manuel, même opération faite par l'API Part), et deux scénarios utilisateur complets
(`install/scenario_test.py`). Tout ce qui suit est corrigé, testé (37/37) et poussé.

### 11.1 Mesures des couches qui pouvaient dire OK sur une pièce fausse

| Mesure | Défaut | Maintenant |
|---|---|---|
| Boîte englobante | `Shape.BoundBox` : loft 30×20 lu 37,3×26,8 ; révolution B-spline lue plus petite (une interférence ratée) | `optimalBoundingBox` partout |
| Trou débouchant | comparé à l'étendue de toute la pièce : équerre en L, lamage, trou incliné lus « borgnes » | ouvert aux deux bouts, jugé sur les faces d'extrémité |
| Trous en B-spline | STEP d'un autre CAO : aucun trou vu | cylindre ajusté sur la face |
| Porte-à-faux | normale médiane seule : trou horizontal, sphère, rond couché = 0 mm² | mesuré sur la face (≤ 1 %) ; 45° pile n'est pas un porte-à-faux |
| Épaisseur de paroi | rayons échantillonnés : trou à 0,3 mm d'un bord lu 0,81 ; arête vive de trous sécants lue 0,03 | faces proches mesurées deux à deux ; un coin n'est pas une paroi |
| Body | fonction après la Tip ou supprimée : OK sans le trou | FAIL ; étape ≠ pièce (export/plan/FEM/imprimabilité refusent une étape) |
| `no_interference` | la cible ignorée | la cible incluse |
| Nomenclature | pièce gauche = pièce droite | « (mirrored) » sur sa propre ligne |

### 11.2 Bugs de la base trouvés en mesurant les volumes produits

Congé/chanfrein « toutes arêtes », coque, lissage, balayage créés à côté du Body (inchangé) ;
fraisage sous la pièce (ne coupait rien) ; lamage sur la face du dessous ; trou borgne depuis le
haut de toute la pièce ; révolution/rainure/hélice autour de l'axe de l'esquisse au lieu de celui
nommé ; nervure de volume nul ; extrusion/révolution Part sans les trous de l'esquisse ; coupe
ratée au-delà de 500 mm ; `verify_sketch` (aire du premier contour) ; `list_faces` (normale
arbitraire sur une face courbe). Détail : `server/freecad-mcp/CHANGES-NikeTheBee.md`.

### 11.3 Robustesse

Course au démarrage : deux FreeCAD lancés ensemble, le perdant écrasait le jeton du gagnant →
tous les appels refusés jusqu'au redémarrage (vu comme un échec « aléatoire » de la CI). Corrigé
(jeton publié après le `bind` exclusif) ; l'appel dont le FreeCAD perd la course obtient le
gagnant. Nouvel outil `export` (fichier relu et comparé au solide).

### 11.4 Requêtes, vérifications et mécanismes (suite)

| Outil | Défaut | Maintenant |
|---|---|---|
| `face_relationship` | aire de recouvrement jamais donnée (« edges found but no closed wire ») | aire de l'intersection des faces (25 mm² exacts) |
| `clearance` | deux pièces qui se chevauchent de 500 mm³ : « TOUCHING » | « INTERFERING — 500 mm³ » ; contact franc : TOUCHING |
| `batch_interference` | deux pièces posées l'une sur l'autre comptées en collision | listées « Touching », pas en collision |
| `verify_orientation`, `list_faces` | normale prise en (0, 0) : un dôme vers +Z échouait | normale au centre de la face |
| `verify_no_self_intersection` | composé de deux solides qui se chevauchent : « valide » | contrôle booléen (BOP) |
| `mesh_to_solid` | maillage ouvert : « solide » invalide de 5478 mm³ (vrai 6000) | gardé en coque, dit « PAS un solide », sans volume |
| fixtures | la sauvegarde maillait la pièce : le loft inchangé « différait » aussitôt | boîte exacte |
| `get_volume`, centre de masse | chevauchement compté deux fois (2000 au lieu de 1500 mm³) ; coque ouverte « 800 mm³ » ; composé : erreur | volume de matière (fusion), pas de volume sans solide |
| tableur, VarSet | valeur qui casse la pièce : « Set … » | la réponse nomme les objets en erreur |
| `check_assembly` | une esquisse comptée comme pièce : OK silencieux ; coque : volume faux | refusées (pièces solides seulement, pas une étape de Body) |
| cinématique 4 barres | la loi dépendait de l'angle de départ du balayage (−208,5° ou +35,7° au même angle) | mode d'assemblage fixé à la référence, sortie continue |
| `contains_point` | coque ouverte : réponse « dedans » sans intérieur ; composé qui se chevauche : point du 2e solide « dehors » | refusé sans intérieur ; testé solide par solide |
| contrat `hole_at` | comparait le milieu de l'axe : un trou D5 « en (10, 10, 20) », z étant la face d'où il part, échouait sur la bonne pièce | tout point de l'axe entre ses deux bouts |
| `holes` (analyse, contrat) | 4 trous lamés comptés 8 ; deux trous coaxiaux de deux flasques lus comme UN alésage de 24 mm à travers l'air ; deux trous borgnes opposés lus comme UN trou débouchant | un alésage = un tronçon continu ; un trou = ses alésages qui se touchent ou ne sont séparés que d'air (lamage, chape, perçage croisé) ; le contrat compte les trous |
| contrat `volume`/`mass` | une face : 0 g, donc « masse max 60 g » OK sur une esquisse ; coque ouverte : 800 mm³ sans sens ; deux pièces qui se chevauchent : 2000 au lieu de 1500 mm³ | FAIL sans solide fermé (avec la raison) ; volume de matière (fusion) |
| nomenclature (BOM) | volume pile sur une limite d'arrondi (plaque 12,5 × 10,5 × 2,5 = 328,125 mm³) : 40 plaques identiques tournées sur deux lignes (15 + 25) | signatures comparées à 1e-6 près, pas arrondies |
| plan 2D (4 vues) | échelle calculée sur la 1re case : la vue iso d'un cube de 45 mm à 1:1 débordait de 14 mm sur le cartouche, verdict OK | échelle par case ; une vue hors de sa case : FAIL |
| tests sous `freecadcmd` | `sys.exit(1)` jette toute la sortie non vidée : un test en échec n'affichait rien, pas même sa trace | sortie vidée avant chaque `sys.exit` |
